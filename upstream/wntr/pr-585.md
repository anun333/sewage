**Title:** Number the evaluator's variables and constraints in creation order, so WNTRSimulator runs repeat (#585)

## Summary

Fixes #585. `Evaluator` kept its variables and constraints in `std::set<T*>`, ordered by pointer value, and `set_structure()` numbered them in that order. So the Jacobian's rows and columns followed heap addresses, which change from run to run, and so did the rounding of each Newton step.

This PR (`evaluator.hpp`, `evaluator.cpp`):
- gives each `Var`, `Constraint` and `IfElseConstraint` a creation serial (`serial`, set in `Evaluator::add_var`, `add_constraint` and `add_if_else_constraint`), and orders `var_set`, `con_set` and `if_else_con_set` by it (`SerialLess<T>`);
- sorts each row's Jacobian terms by column index in `set_structure()`. The terms stay in `std::map<Var*, ...>`, ordered by address, because those members' types appear in the SWIG wrapper; sorting there leaves `evaluator_wrap.cpp` unchanged.

Python already creates variables and constraints in a fixed order (`aml.py` and `expr.py` use `OrderedDict` and `OrderedSet` throughout), so the numbering now repeats from run to run. `param_set` and `float_set` are unchanged: their order only decides the order of deletion.

## Tests and Documentation

- **New test.** `TestStructureOrder.test_creation_order` in `test_aml.py`:
  - builds 50 constraints, removes 25, adds 25 more, then adds one that uses old and new variables;
  - checks that constraint and variable indices follow creation order, and that every Jacobian row's columns are sorted.

  On `main` it fails: the constraint indices come out `[15, 18, 17, 19, 16, 13, 12, 14, 20, 27, ...]`, because new objects reuse freed, lower addresses. With this PR it passes.
- **Test suite, x86-64 Linux** (Debian 13, Python 3.13.5, gcc 14.2), CI's core selection (`pytest -m "not extensions" --doctest-modules --doctest-glob="*.rst" wntr`): `main` 470 passed, this PR 471 (the new test), the same 6 skipped. The final version, which reuses one scratch vector per `set_structure()` call, was run again: 471 passed, and its results on every network are bit-identical to the first version's.
- **Test suite, aarch64 Linux** (Debian 13, Neoverse-N1), CI's quick selection: the same 71 failures as `main`, all of them EPANET loads (#584), and the new test passes.
- **Repeat runs.** Every network in `examples/networks` that the issue used (Net1, Net2, Net3, Net6, ky4, ky10), plus EPANET's Net1-3, through `WNTRSimulator`. Four runs each of `main` and of this PR: three in fresh processes with string hashing and address randomisation on, as a user gets, and one with `PYTHONHASHSEED` fixed, randomisation off and a longer environment.
  - **x86-64.** On `main`, all 41 result variables of the eight converging networks differ between all four runs (ky10 doesn't converge, and repeats either way). With this PR, all four runs are bit-identical.
  - **aarch64.** On `main` all 41 variables vary between runs, and 40 of them come out different in all four. With this PR none vary.
  - **Against `main`**, the results move no more than `main`'s runs move among themselves.
    - On Net6, head at JUNCTION-1100 differs from `main`'s runs by up to 7.2 m, while `main`'s runs differ from each other by up to 7.21 m.
    - On the other networks, the largest difference is 4e-12 in SI units, a velocity on ky4. The largest relative difference is 5e-8, on flows near zero, the same as between `main`'s own runs. Everything passes `allclose` (rtol 0.01, atol 1e-6).
- **Speed** (x86-64, one process at a time on one core, `main` and this PR alternating):
  - **`set_structure()`**, which runs before every solve, takes 3.11 ms per call with this PR against 2.68 ms on `main`, 16% more (Net6, eight runs each; 2.75-3.51 ms against 2.40-3.00 ms). The extra time is building and sorting each row's terms.
  - **On a whole run**, `set_structure()` is under 2% of a Net6 run, so that's about 0.25% (0.31 s of 128 s).
  - **Net6's total times can't be compared directly**, because `main` takes a different control path on almost every run (724 to 819 solves; this PR always takes 724). They were 125.8-139.8 s on `main` and 125.0-132.6 s with this PR.
  - **Net3 and Net2 take the same path** either way (183 and 56 solves). Five runs each on Net3: 0.70-0.75 s on `main`, 0.71-0.74 s with this PR (means 0.722 and 0.730 s). On Net2, 0.07-0.09 s for both.
  - In those runs `main`'s Net3 and Net2 pressures came out different in every one of the five; this PR's were the same in all five.
- **Compilers.** `evaluator.cpp` compiles as C++98 and C++17 with g++ 14.2 and clang 19, with the same 11 `-Wall -Wextra` warnings as `main`.
- **SWIG.** The committed `evaluator_wrap.cpp` builds unchanged. I also regenerated it with SWIG 4.0.2 (`-c++ -python -builtin`, as `setup.py`'s `use_swig` does):
  - from `main`'s sources, it reproduces the committed `evaluator_wrap.cpp` and `evaluator.py` byte for byte;
  - from this PR's sources, `evaluator.py` is unchanged and the wrapper gains only get/set accessors for the three `serial` members, plus SWIG's `size_t` conversions;
  - a build with that regenerated wrapper passes `test_aml.py`.

  If you'd rather not expose `serial` to Python when you next regenerate, an `%ignore` or `%immutable` line in `evaluator.i` would hide it.

No documentation change.
